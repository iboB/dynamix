# Messages

Messages are the main way to get polymorphic behavior from DynaMix objects. They are the DynaMix counterpart of virtual methods.

The term "message" is used in the same sense as in Smalltalk or Objective-C: the message is what is *called*, and the method is what is *executed*. Calling a message for an object finds the mixin (or mixins) in the object which implement it and executes their implementations. The code which calls the message doesn't know or care what the object is composed of.

Messages are a type of [mixin feature](../basics/glossary.md#mixin-feature). Everything said here about overriding, bids, and priorities applies to features in general. Messages are just the most common feature and the one the library provides out of the box.

> [!TIP]
> All code on this page is from [example/guide/messages.cpp](../../example/guide/messages.cpp). It's a complete program which is built and run with the library's tests. In it a game character is composed of traits, forms, and status effects. Reading it top to bottom alongside this page is a good idea.

## Declaring messages

```c++
#include <dynamix/msg/declare_msg.hpp>

// unicast: one implementation is executed per call
DYNAMIX_DECLARE_MSG(get_name_msg, get_name, std::string, (const dynamix::object&));
DYNAMIX_DECLARE_MSG(speak_msg, speak, std::string, (const dynamix::object&));

// multicast: all (top-bid) implementations are executed per call
DYNAMIX_DECLARE_MSG(describe_msg, describe, void, (const dynamix::object&, std::vector<std::string>&));

// a non-const message: implementations can modify the mixins
DYNAMIX_DECLARE_MSG(rename_msg, rename, void, (dynamix::object&, std::string));
```

`DYNAMIX_DECLARE_MSG(msg_name, func_name, return_type, args)` declares two things:

* A type, `msg_name`, which identifies the message. You use it when you refer to the message itself: to say that a mixin implements it, to query whether a type implements it, and so on.
* A function, `return_type func_name args`, which calls the message.

The first argument in `args` is the object. It must be a reference to `dynamix::object` or to a class derived from it. Its constness matters:

* `const dynamix::object&` - the message can be called for const objects. Mixins implement it with const methods.
* `dynamix::object&` - the message can only be called for non-const objects. Mixins implement it with methods which can modify them.

The declaration says nothing about whether the message is a unicast or a multicast. This is decided when the message is [defined](#defining-messages), and users who call it don't need to know.

## Implementing messages

Mixins state which messages they implement in their definition:

```c++
#include <dynamix/define_mixin.hpp>

struct person {
    std::string name;
    person(std::string n) : name(std::move(n)) {}

    std::string get_name() const { return name; }
    void rename(std::string n) { name = std::move(n); }
    void describe(std::vector<std::string>& out) const {
        out.push_back("a person");
    }
};

DYNAMIX_DEFINE_MIXIN(game, person)
    .implements<get_name_msg>()
    .implements<rename_msg>()
    .implements<describe_msg>(1_prio) // higher priority: described first
;
```

### With methods

`.implements<Msg>()` binds the message to a method of the mixin with the same name as the message function: `get_name_msg` to `person::get_name`, `rename_msg` to `person::rename`. The method's arguments are the message's arguments without the object.

For this to work, the code which defines the mixin needs to see the *function traits* for the function name, generated by `DYNAMIX_MAKE_FUNC_TRAITS`:

```c++
#include <dynamix/msg/func_traits.hpp>

DYNAMIX_MAKE_FUNC_TRAITS(get_name);
DYNAMIX_MAKE_FUNC_TRAITS(speak);
DYNAMIX_MAKE_FUNC_TRAITS(describe);
DYNAMIX_MAKE_FUNC_TRAITS(rename);
```

Function traits are generated once per function name, not per message, and must be in the same namespace as the message declarations. They are also needed by the message definitions. A common practice is to put them in a header of their own which is included by the files that define mixins and messages (see [Organizing code](#organizing-code)).

The method doesn't have to be declared in the mixin class itself. Inherited methods work, too.

### With functions

`.implements_by<Msg>(func)` binds the message to a function or a captureless lambda. Its first argument is a pointer to the mixin, followed by the message's arguments:

```c++
DYNAMIX_DEFINE_MIXIN(game, silenced)
    // implement a message with a function or lambda instead of a method
    // the first argument is a pointer to the mixin
    .implements_by<speak_msg>([](const silenced*) -> std::string { return "..."; }, 1_bid)
    .implements<describe_msg>()
;
```

This doesn't require function traits. It's useful when the mixin is a class you can't or don't want to modify, when the method has a different name, or when the implementation is trivial.

For const messages the mixin pointer must be a pointer to const.

### Bids and priorities

Both `implements` and `implements_by` take optional *bid* and *priority* for the implementation. They're specified with the user-defined literals `_bid` and `_prio`, or with the functions `feature_bid(b)`, `order_priority(p)`, and `feature_bid_priority(b, p)`. They're available in `DYNAMIX_DEFINE_MIXIN` without qualification. Both default to zero.

```c++
.implements<speak_msg>(2_bid)
.implements<describe_msg>(1_prio)
.implements<speak_msg>(1_bid, -3_prio)
.implements_by<speak_msg>(func, feature_bid_priority(1, -3))
```

What they do is explained in [Unicasts and overriding](#unicasts-and-overriding) and [Multicasts](#multicasts).

## Defining messages

Each message must be defined exactly once, in a single compilation unit:

```c++
#include <dynamix/msg/define_msg.hpp>

// default implementation of get_name
// it is called with the object as the first argument (not a mixin)
std::string default_name(const dynamix::object&) { return "Someone"; }

// unicast, which does not allow clashes, and has a default implementation
DYNAMIX_DEFINE_MSG_EX(get_name_msg, unicast, false, default_name,
    get_name, std::string, (const dynamix::object&));

DYNAMIX_DEFINE_MSG(speak_msg, unicast, speak, std::string, (const dynamix::object&));
DYNAMIX_DEFINE_MSG(describe_msg, multicast, describe, void, (const dynamix::object&, std::vector<std::string>&));
DYNAMIX_DEFINE_MSG(rename_msg, unicast, rename, void, (dynamix::object&, std::string));
```

`DYNAMIX_DEFINE_MSG(msg_name, mechanism, func_name, return_type, args)` repeats the arguments of the declaration and adds the *mechanism*: `unicast` or `multicast`.

`DYNAMIX_DEFINE_MSG_EX(msg_name, mechanism, allow_clashes, default_impl, func_name, return_type, args)` additionally sets:

* `allow_clashes` - whether two mixins in a type may implement the message with the same bid and priority. See [Clashes](#clashes).
* `default_impl` - a function which is called when an object has no mixins that implement the message, or `nullptr`. See [Default implementations](#default-implementations).

`DYNAMIX_DEFINE_MSG` is the same as `DYNAMIX_DEFINE_MSG_EX` with clashes allowed and no default implementation.

## Calling messages

A message is called through its function:

```c++
std::cout << get_name(hero) << " says: " << speak(hero) << '\n';
rename(hero, "Alicia");
```

The same can be achieved with the static member `call` of the message type: `speak_msg::call(hero)`. This is mostly useful in generic code, and for [simple messages](#simple-messages) which have no function.

A message call does a constant-time lookup in the object's type and an indirect function call, comparable to `std::function`. It's as thread-safe as the implementation which ends up being executed: calling messages doesn't modify the object or its type.

If an object has no implementation for a message and the message has no default implementation, the call throws `dynamix::feature_error`:

```c++
object hero(g::get_domain<game>());

// speak has no default implementation, so calling it throws
try {
    speak(hero);
}
catch (const feature_error& e) {
    std::cout << "error: " << e.what() << '\n';
}
```

```
error: game: {} does not implement dynamix msg 'speak_msg'
```

> [!WARNING]
> Mutating the object from within a message implementation needs care. It's similar to calling `delete this` from a method. See [Dangerous Functionalities](../advanced/danger.md#mutating-an-object-within-a-message).

## Unicasts and overriding

When a unicast is called, exactly one implementation is executed. When several mixins in an object implement the same unicast, the one which is executed is said to *override* the others. With C++ inheritance overriding is decided by the class hierarchy. With DynaMix it's decided at run time by the *bid*, *priority*, and *order* of the mixins in the object's type.

### By order

When implementations have the same bid and priority, the mixin which comes last in the object's type wins:

```c++
mutate(hero, add<person>("Alice"), add<human_voice>());
std::cout << get_name(hero) << " says: " << speak(hero) << '\n';
// Alice says: Hello

// dragon_form also implements speak_msg with the same bid
// the last mixin in the type wins
mutate(hero, add<dragon_form>());
std::cout << get_name(hero) << " says: " << speak(hero) << '\n';
// Alicia says: Roar
```

By default a mixin is added at the end of the type, so the most recently added mixin overrides. This matches the intuition of "adding behavior" to an object, and it's what makes it possible to override features without having to plan bids in advance.

> [!NOTE]
> If the domain is created with `domain_settings::canonicalize_types`, the mixin order in types doesn't depend on the order in which they were added, but is a fixed canonical order. With such domains, overriding by order is not practical and bids and priorities should be used.

### By bid

The bid is the primary way to override. Implementations with a higher bid override all implementations with a lower bid, regardless of the mixin order:

```c++
// silenced implements speak_msg with a higher bid
// it overrides speak regardless of the mixin order
mutate(hero, add<silenced>());
std::cout << get_name(hero) << " says: " << speak(hero) << '\n';
// Alicia says: ...

// removing the status effect restores the previous behavior
mutate(hero, remove<silenced>());
std::cout << get_name(hero) << " says: " << speak(hero) << '\n';
// Alicia says: Roar
```

Note what happened here. The overridden implementation (`dragon_form`'s) didn't go anywhere. It's just not the top one anymore. When the overriding mixin is removed, the object's behavior is restored. This is a natural fit for things like status effects, states, temporary modes, or decorators, which with classic OOP would require extra machinery like a state pattern or a chain of decorator objects.

Overridden implementations are also still *reachable*. See [Calling the next implementation](#calling-the-next-implementation).

### By priority

Priority is a secondary key. It's used to order implementations with the *same* bid. For unicasts, an implementation with a *lower* priority value overrides one with a higher value. For example, an implementation with `-1_prio` would override one with the default priority of `0`, regardless of mixin order.

Priority is more natural for multicasts (see below), and for unicasts bids are usually the better tool.

> [!IMPORTANT]
> This is the opposite of DynaMix v1, where a higher priority overrode a lower one for unicasts. See [Differences Between v1 and v2](../misc/v2-vs-v1.md).

## Multicasts

When a multicast is called, all implementations with the top bid in the object are executed:

```c++
DYNAMIX_DEFINE_MSG(describe_msg, multicast, describe, void, (const dynamix::object&, std::vector<std::string>&));
// ...
mutate(hero, add<dragon_form>(), add<silenced>());
print_description(hero);
// Alicia is: a person; in the form of a dragon; silenced;
```

where `print_description` calls `describe(obj, parts)` once and prints all `parts`.

Multicasts are the DynaMix counterpart of the observer pattern or a signal: the caller sends a message to the object and every interested mixin reacts to it. Since the implementations are part of the type, there is no list of subscribers to manage.

### Execution order

* Implementations with a higher priority are executed first.
* Implementations with the same priority are executed in the order of their mixins in the type.

```c++
// person is added last here, but its describe has a higher priority
// so it is still executed first
object villain(g::get_domain<game>());
mutate(villain, add<dragon_form>(), add<silenced>(), add<person>("Smaug"));
print_description(villain);
// Smaug is: a person; in the form of a dragon; silenced;
```

### Bids

Only implementations with the top bid are executed. Implementations with lower bids are overridden, just like with unicasts. This allows a mixin to override a whole set of implementations: an implementation with a higher bid will be the only one executed. As with unicasts, the overridden implementations are still reachable with [`DYNAMIX_CALL_NEXT_BIDDER_SET`](#calling-the-next-implementation).

### Return value and arguments

A multicast returns the result of the implementation which is executed *last*. This is the same implementation which would be executed if the message were a unicast. The results of the other implementations are discarded. If you need to combine results, pass an output argument, like `describe` does, or an accumulator object.

Arguments are passed to each implementation. This means that arguments which are passed by value are copied for each implementation except the last one, which gets them moved. Use references for expensive arguments.

## How implementations are ordered

For each feature, a type has a list of the implementations of its mixins in the *ftable* (feature table). Knowing how it's ordered explains all of the above. Implementations are sorted by:

1. Bid: higher bids first
2. Priority: lower priorities first
3. Mixin order: mixins later in the type first

Then:

* A unicast executes the first implementation.
* A multicast executes all implementations with the first (top) bid, from last to first. Thus the implementation which a unicast would execute is executed last and its result is returned.

## Calling the next implementation

An implementation can call the implementation which it overrides. This is the DynaMix counterpart of calling the base class method from an overriding virtual method (`Base::method()`). The difference is that the mixin doesn't know which implementation that is, and it can be different in different objects.

```c++
#include <dynamix/msg/next_impl.hpp>

struct shouting {
    std::string speak() const {
        // call the implementation of speak_msg which is next in line after this mixin
        auto str = DYNAMIX_CALL_NEXT_IMPL_MSG(speak_msg);
        for (auto& c : str) c = char(std::toupper(c));
        return str + "!";
    }
};

DYNAMIX_DEFINE_MIXIN(game, shouting)
    .implements<speak_msg>(2_bid)
;
```

```c++
// shouting has the highest bid and calls the next implementer
mutate(hero, add<shouting>());
std::cout << get_name(hero) << " says: " << speak(hero) << '\n';
// Alicia says: ROAR!

mutate(hero, remove<dragon_form>());
std::cout << get_name(hero) << " says: " << speak(hero) << '\n';
// Alicia says: HELLO!
```

`shouting` decorates whatever the object's speech is: the dragon's roar, the human's hello, or anything else that may be added in the future.

These macros are used in mixin methods (they use `this`):

| Macro | Description |
|---|---|
| `DYNAMIX_CALL_NEXT_IMPL_MSG(msg, args...)` | Call the next implementation of `msg` after this mixin. Throws `feature_error` if there is none. |
| `DYNAMIX_HAS_NEXT_IMPL_MSG(msg)` | Check whether there is a next implementation of `msg` after this mixin. |
| `DYNAMIX_CALL_NEXT_BIDDER_SET(msg, args...)` | Call all implementations of `msg` with the next lower bid, as a multicast would. Throws `feature_error` if there are none. |
| `DYNAMIX_CALL_NEXT_BIDDER_TOP(msg, args...)` | Call only the top implementation from the next bidder set, as a unicast would. |
| `DYNAMIX_HAS_NEXT_BIDDER_SET(msg)` | Check whether there is a set of implementations of `msg` with a lower bid. |

The equivalent functions without macros are `dynamix::call_next_impl_msg<Msg>(mixin_ptr, args...)` and so on in [next_impl.hpp](../../code/dynamix/msg/next_impl.hpp). They can be used in functions which implement messages with `implements_by`.

Default implementations are not reachable this way.

## Default implementations

A message can have a default implementation. It's executed when the object has no mixins which implement the message. Unlike regular implementations, it receives the object as its first argument (instead of a mixin):

```c++
std::string default_name(const dynamix::object&) { return "Someone"; }

DYNAMIX_DEFINE_MSG_EX(get_name_msg, unicast, false, default_name,
    get_name, std::string, (const dynamix::object&));
```

```c++
object hero(g::get_domain<game>());
// the object is empty, but get_name has a default implementation
std::cout << get_name(hero) << '\n';
// Someone
```

Default implementations are useful for messages which have a reasonable answer for objects that don't care about them, for example `get_name` returning a placeholder or `update` doing nothing. This frees mixins from the need to provide dummy implementations and callers from the need to check whether a message is implemented.

A default implementation can use the object to do anything a regular function can: call other messages, query mixins, and so on.

## Clashes

Two implementations *clash* when they have the same bid and priority in a type. By default this is allowed, and the order of the mixins decides which one overrides.

When a message is defined with `allow_clashes` set to `false`, such types are considered an error. A mutation which would lead to one throws `dynamix::type_error`:

```c++
// get_name_msg does not allow clashes:
// impostor implements it with the same bid and priority as person
try {
    mutate(hero, add<impostor>());
}
catch (const type_error& e) {
    std::cout << "error: " << e.what() << '\n';
}
```

```
error: game: feature clash in {'person', 'human_voice', 'shouting', 'dragon_form', 'silenced', 'impostor'} on 'get_name_msg' between 'impostor' and 'person'
```

The object is not modified when this happens.

Disallowing clashes is useful for messages for which overriding by order is likely a bug, for example ones which identify the object, or when a domain canonicalizes types and the order of mixins is not meaningful.

## Querying

Since messages are features of the type and not of the object, you can check whether a type implements a message without calling it, and even without having an object:

```c++
// `implements` is true for features with a default implementation, too
// `implements_strong` is only true if a mixin implements it
object nobody(g::get_domain<game>());
const type& t = nobody.get_type();
std::cout << std::boolalpha
    << "nobody implements get_name: " << t.implements<get_name_msg>()
    << ", strong: " << t.implements_strong<get_name_msg>() << '\n'
    << "hero implements speak: " << hero.get_type().implements<speak_msg>() << '\n';
```

```
nobody implements get_name: true, strong: false
hero implements speak: true
```

For more complex queries, see [Type Classes](type-classes.md).

## Overloads

Several messages can share the same function name, as long as the function signatures are different:

```c++
DYNAMIX_DECLARE_MSG(set_pos_msg, set_pos, void, (dynamix::object&, int, int));
DYNAMIX_DECLARE_MSG(set_pos_vec_msg, set_pos, void, (dynamix::object&, vec2 pos));
```

The functions are overloads of `set_pos`, while the messages are different: `set_pos_msg` and `set_pos_vec_msg`. A mixin implements each separately, and with `implements` they bind to the corresponding method overloads in the mixin. A single `DYNAMIX_MAKE_FUNC_TRAITS(set_pos)` serves all of them.

Overloading on the constness of the object argument works too. It allows a mixin to have a const and a non-const method with the same name and implement a different message with each.

## Simple messages

Simple messages have no function and no binding to methods. They're declared with a function signature:

```c++
DYNAMIX_DECLARE_SIMPLE_MSG(get_hp, int(const dynamix::object&));
DYNAMIX_DEFINE_SIMPLE_MSG(get_hp, unicast);
// or with clash and default implementation
DYNAMIX_DEFINE_SIMPLE_MSG_EX(get_hp, unicast, false, default_hp_func);
```

They're called with the `call` member, `get_hp::call(obj)`, and implemented with `implements_by`:

```c++
DYNAMIX_DEFINE_MIXIN(game, creature)
    .implements_by<get_hp>([](const creature* c) { return c->hp; })
;
```

They're slightly less convenient to use, but they don't need function traits, and they don't add a function name to the namespace.

## Organizing code

In a project with many files a typical organization would be:

* **Message declarations** in a header (e.g. `messages.hpp`). This is all that code which calls messages needs.
* **Function traits** in a header (e.g. `messages_traits.hpp`). It's included where mixins and messages are defined.
* **Message definitions** in a source file (e.g. `messages.cpp`), which includes both headers.
* **Mixin definitions** in source files which include the message declarations and function traits.

Calling messages doesn't need the definitions of mixins or messages. This means that code which uses objects doesn't need to recompile when mixins are added, removed, or changed, which can noticeably improve build times in large projects.

When messages are part of a shared library, use the `EXPORTED` variants of the declaration macros. They take an export macro (like `MYLIB_API`) as their first argument:

```c++
DYNAMIX_DECLARE_EXPORTED_MSG(MYLIB_API, speak_msg, speak, std::string, (const dynamix::object&));
DYNAMIX_DECLARE_EXPORTED_SIMPLE_MSG(MYLIB_API, get_hp, int(const dynamix::object&));
```

The definition macros are the same for exported and non-exported messages. See the [app-plugin test](../../test/app-plugin/) for a complete example of messages in a shared library which are implemented in plugins.

| Macro | Header | Description |
|---|---|---|
| `DYNAMIX_DECLARE_MSG(msg, func, ret, args)` | `msg/declare_msg.hpp` | Declare a message and its function |

| `DYNAMIX_DECLARE_SIMPLE_MSG(msg, signature)` | `msg/declare_msg.hpp` | Declare a simple message |
| `DYNAMIX_DECLARE_EXPORTED_SIMPLE_MSG(export, msg, signature)` | `msg/declare_msg.hpp` | Same, for shared libraries |
